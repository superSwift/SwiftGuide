# 无图形优先 -> 图形化升级路线图（可扩展架构）

> 你的思路完全可行：先跑通无图形核心，等你熟悉后再升级 UI。

## 1. 总体原则

1. **先稳定内核**：数据、策略配置、回测、调度先跑通
2. **接口先行**：所有能力都通过 API 暴露，UI 只是 API 的“一个客户端”
3. **可插拔扩展**：后续接 UI、模型、风控、实盘时，不推翻现有系统

---

## 2. 三阶段实施路线

### Phase 1（现在）：Headless Core

目标：没有图形界面也能完整工作。

- Data API：A股行情/财务查询
- Strategy API：策略 CRUD + 校验
- Backtest API：回测任务执行与报告
- Scheduler：定时运行
- 审计日志：任务、参数、版本可追踪

交互方式：AI 对话 + JSON 配置 + 报告文件。

### Phase 2（后续）：Management UI

目标：在不改内核逻辑前提下，增加可视化操作入口。

- 策略列表与版本管理
- 策略参数表单编辑
- 回测任务发起与进度查看
- 回测报告图表化展示

建议：优先 Streamlit，后续可替换为 React/Vue。

### Phase 3（升级）：Advanced Extensions

目标：扩展能力而不破坏现有 API。

- 多策略组合与组合优化
- 因子研究与模型评分
- 风控中心（仓位约束、回撤保护）
- 模拟盘/实盘网关（可选）

---

## 3. 为后续升级预留的关键设计

## 3.1 API 版本化

- 建议使用 `/api/v1/...`
- 后续新增字段尽量“向后兼容”

## 3.2 策略 Schema 版本

- 每个策略保存 `schema_version`
- UI 升级时可做自动迁移（v1 -> v2）

## 3.3 任务与结果分离

- `task_run` 保存执行元数据
- `task_result` 保存结果与指标
- 有利于后续接 UI 监控与告警

## 3.4 插件化执行器

- 回测引擎抽象成 `engine_type`
- 初期 `backtrader`，后续可接 `qlib` 等

## 3.5 统一指标字典

- 收益、回撤、夏普、换手、成本统一定义
- 避免后续 UI/报告口径不一致

---

## 4. 你关心的问题：后续加 UI 会不会重做？

不会，如果我们现在按“API-first + schema-first”做：

- Headless 与 UI 共用同一套后端接口
- UI 只是“调用接口 + 展示结果”
- 内核（数据/回测/调度）基本不需要推翻

这就是先无图形再图形化的最大优势。
